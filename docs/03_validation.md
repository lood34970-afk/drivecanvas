# Drive Canvas — 검증 계획

## 검증 목표

이 아이디어의 성패는 그림 템플릿 수가 아니라 `안전하게 주행 가능한 그림 경로를 만들고 차량 내비로 그대로 안내할 수 있는가`에 달려 있다. 아래 순서로 가장 큰 실패 가설부터 확인한다.

## 가설 목록

| 우선순위 | 가설 | 검증 방법 | 통과 기준 | 상태 |
|---:|---|---|---|---|
| 1 | 도로망 위에서 알아볼 수 있는 하트를 만들 수 있다. | 성격이 다른 3개 지역에서 하트 투영·라우팅 실험 | 3곳 중 1곳 이상에서 위험 조건 없이 제3자 인지 테스트 통과 | 대기 |
| 2 | 생성한 경유지 순서가 차량 내비 경로에서 유지된다. | NaviHelper 최소 앱으로 경유지 수·순서·재탐색 시험 | MVP 코스가 한 번의 안내 세션으로 실행되거나 안전한 대체 방식 확인 | 대기 |
| 3 | 운전 중 최소 UI만으로 코스를 완주할 수 있다. | 에뮬레이터 과업 테스트와 주의분산 가이드 대조 | 주행 중 편집 없이 TBT·음성만으로 과업 완료 | 대기 |
| 4 | 사용자가 결과를 다시 만들고 싶어 한다. | 타깃 5명 콘셉트·결과 카드 테스트 | 3명 이상이 구체적인 사용 상황과 두 번째 코스를 선택 | 대기 |
| 5 | 관광형 포지셔닝이 불필요한 주행 우려를 줄인다. | 개인 놀이형과 지역 코스형 설명 비교 인터뷰 | 지역 코스형의 이용 의향·수용성이 더 높음 | 대기 |

## 기술 스파이크 A — 경로 생성

### 입력

- 단순한 하트 벡터 1개
- 자동차 통행 방향과 도로 등급이 포함된 소규모 도로 그래프
- 출발지 복귀, 30~45분 목표

### 산출물

- 특징점과 경유지 목록
- 실제 라우팅 polyline
- 형태 유사도, 거리, 예상 시간, 회전 수
- 제외된 도로와 실패 이유

### 최소 안전 조건

- 금지 방향과 자동차 진입 불가 도로를 사용하지 않는다.
- 불법 유턴을 요구하지 않는다.
- 같은 짧은 구간의 불필요한 반복을 제한한다.
- 위험 조건을 만족하지 못하면 경로 없음으로 종료한다.

## 기술 스파이크 B — Pleos 연결

확인 항목은 다음과 같다.

- NaviHelper의 목적지·경유지 설정 방식과 최대 개수
- 경유지 순서 보존 여부
- 안내 시작, TBT, 경로 이탈, 재탐색, 도착 이벤트
- 앱이 만든 경로와 내비게이션이 실제 선택한 polyline의 차이
- FusedLocation 또는 허용 위치 API의 갱신 주기와 궤적 정확도
- 주행·정차 상태에 따라 설정과 결과 화면을 잠그는 방법
- 네트워크·권한·capability 미지원 시의 종료 동작

## 사용자 검증

### 대상

- 월 1회 이상 여가 드라이브를 하는 운전자 5명 이상
- 커플·가족 여행에서 운전하는 사용자 포함

### 보여 줄 것

- 같은 지역의 일반 드라이브 경로와 하트 경로
- 주행 전 후보 비교 화면
- 주행 중 최소 안내 화면
- 완주 카드 두 가지 버전: 개인 놀이형, 지역 관광형

### 질문보다 관찰할 행동

- 설명 없이 어떤 서비스인지 이해하는가?
- 시간·거리·모양 중 무엇을 먼저 비교하는가?
- 실제로 달릴 코스를 하나 선택하는가?
- 결과 그림을 정확히 알아보는가?
- 두 번째로 만들 그림이나 사용할 상황을 스스로 제시하는가?

## 계속·수정·중단 기준

- `계속`: 하트 코스와 내비 안내가 연결되고, 사용자 다수가 구체적인 이용 상황과 재사용 의사를 보임
- `수정`: 자동 생성은 불안정하지만 검수된 코스의 이용 의향이 있음 → 지역 관광 코스 플랫폼으로 전환
- `중단`: 검수된 코스도 안전한 안내가 어렵거나, 결과 콘텐츠에 대한 실제 선택 행동이 거의 없음

## 첫 번째 작업 순서

1. NaviHelper 경유지·재탐색 제약을 공식 문서와 최소 코드로 확인한다.
2. 테스트 지역 하나를 정하고 하트 경로를 수동으로 만들어 기준 답안을 만든다.
3. 반자동 투영·라우팅 실험으로 같은 수준을 재현한다.
4. 실제 안내 결과와 목표 polyline의 차이를 측정한다.
5. 완주 화면을 만든 뒤 제3자 그림 인지 테스트를 진행한다.
